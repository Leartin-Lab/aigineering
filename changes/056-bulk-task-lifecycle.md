# Bulk task lifecycle commands

Task operators can now apply signed block, cancel, exact unblock and promotion operations to multiple Contracts in one CLI invocation. Each target remains an independent Candidate publication through the existing task application owner, so a failed target does not undo accepted siblings and the command reports every target result before returning a nonzero exit code.

The commands accept up to 64 unique, nonblank Contract IDs. Bulk block, unblock and cancel derive stable per-target idempotency keys from the returned batch base and exact target. Existing single-target defaults and direct keys remain in place; an operator can replay one target from a previous batch by passing its returned actual key. Multi-target promotion retains its historical `<base>:promote:<contract_id>` key derivation. Unblock requires one exact `--hold-for TASK_ID=HOLD_ID` mapping per selected target. Promotion accepts a complete exact hold mapping per target for replay; without it, promotion retains its existing current-hold discovery behavior. Existing single-target `--hold` and promotion behavior remain available.

JSON batch results preserve input order and distinguish accepted, rejected, missing, Redis-pending, outcome-unknown and not-attempted targets. Accepted operations whose Redis relay is pending include their exact durable result and fact IDs; this does not infer durable authority from Redis. The collector reports an unknown exception by safe class, retains its exception chain, marks later targets not attempted and exits nonzero. SQLite facts remain authoritative, and Redis remains required application collaboration infrastructure.

Cancellation now uses a shared task publication owner rather than compiling the effect in the CLI. It preserves the prior single-target reason trimming, deterministic legacy key and causal parent. A post-commit Redis failure reports retained facts and the Candidate acceptance state separately. Exact replay verification compares the complete RuntimeRecord identity fields and excludes only `recorded_at`, which is not part of record identity; results return the original durable record and timestamp.

This change adds no batch transaction, mutable batch ledger, second scheduler, or provider execution. Each target retains current authorization, signed Candidate admission, writer-time checks, and task-specific effect semantics.
