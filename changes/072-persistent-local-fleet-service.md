# Persistent local Fleet service

The existing `aig fleet run --config ... --task ...` remains a bounded task-root run. A new local service lifecycle provides `aig fleet start`, `status`, `stop`, and `restart` for persistent domain-wide pull dispatch using the same canonical claim, WorkerHost, invocation, renewal, submission, and Redis synchronization owners.

The service is limited to the selected workspace's normal `.aig/store.db`; it rejects custom and in-memory Fleet stores before Worker registration. Existing configured and bounded Fleet runs keep their prior custom `db_path` support. Fleet adapter/resource preparation is shared with configured runs. Start pins the initialized Genesis, config digest, and one process generation before any signed registration setup. Registration remains an ordinary signed operation. Process metadata is private local observation, not task state or authority.

A process lock arbitrates one service generation per workspace. Control messages name the exact generation; a PID is never used as authority to signal a process. Stop closes admission to later claim pulls and drains already admitted pulls; one admitted pull racing with the stop request may still commit a claim and invoke. Stop never resets a claim or cancels a task. Restart waits for the exact prior lock owner to finish, then explicitly validates the new configuration. Config changes are reported as drift and are not hot-reloaded.

The service uses required Redis for operational claims, record relay, and wakeups. SQLite remains the fact and claim authority. Status and stop inspect only local process metadata and remain usable while Redis is unavailable. Idle service cycles do not create a service-owned task queue or synthetic progress; canonical runtime maintenance may still emit its normal expiry, completion, or recovery facts.

Before creating a generation or registering Workers, start checks that each configured LLM worker has a non-empty credential in its configured environment variable or the existing LLM fallback environment variables. It never writes the credential to service metadata. Local and tool workers need no provider credential.

Start also builds the configured adapters through the shared Fleet resource-preparation owner before launching the service process. The child then builds its own process-local adapters through that same owner. A configured local `worker_factory` retains the existing strict `module:callable` format and is invoked once for preflight and again for the service process; no new path-based factory loader is introduced. Unsafe or malformed prior service metadata fails closed. A valid stale generation can be replaced only after the exclusive process lock is acquired and its workspace/schema/generation metadata is validated. After launch, the child owns service state updates, so a fast child startup failure is not overwritten by the parent.

The author validation used isolated copied source, focused tests, a provider-independent local Worker, temporary workspaces, and native Redis DB 14 without flushing it. It did not run a provider, full suite, build, or installed-artifact test. Independent review and integrated release checks remain outstanding. The implementation relies on POSIX file locks and no-follow file access; Windows and multi-user service control are not qualified. Stop/crash cannot guarantee exactly-once external Worker effects.
